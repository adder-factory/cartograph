# Cartograph v2.1.37

Cartograph v2.1.37 fixes two failures that surfaced while upgrading
projects to v2.1.36. A schema migration that waits on another Cartograph
process no longer stalls that process's readers or reports a permanent
failure: it retries and, if the schema stays busy, reports a retryable
`schema_busy`. A full rebuild of a large project no longer fails in the
`reduce` stage, and a failed index no longer strands its lease behind a
cleanup failure.

## Schema migrations under contention

Migration 46 changes a constraint on `index_generations`, which needs an
exclusive table lock. When another Cartograph process, typically a
long-running MCP server started from an older binary, kept transactions open
on that table, the migration waited in PostgreSQL's lock queue until its
60-second statement timeout. Every new reader of the table waited behind it
meanwhile. The failure was then reported as a generic database error, and
`cartograph upgrade --apply` showed the database step as `blocked`, pointing
at `doctor`.

- Each migration attempt runs in one transaction that waits at most 2 seconds
  for any lock. A contended attempt rolls back whole and is retried after a
  1-second pause, for about 5 minutes (the last attempt may finish just past
  that). Another session's readers wait at most 2 seconds behind a queued
  schema change.
- If the schema stays busy for the whole wait, the migration applies nothing
  and reports the new, retryable `schema_busy` code. `cartograph db start`
  exits with status 75 for it, `index --format json` and MCP report it as
  `schema_busy`, and `cartograph upgrade --apply` reports the step as
  `another_writer_active` with `reason: schema_busy` and `retryable: true`.
  The next step names the usual cause: restart or stop the other Cartograph
  process, then rerun the same upgrade. See
  [Troubleshooting](../TROUBLESHOOTING.md).
- The managed database's readiness wait no longer includes the migration, so
  a contended migration is not reported as a readiness timeout.
- `cartograph install` stops when the managed database start fails, and
  `doctor --fix` names a busy schema as the cause.

## Full rebuilds no longer fail in the `reduce` stage

A full rebuild of a 7,075-file TypeScript project failed after about five
minutes with `reduce_failed` and a secondary `cleanup_failure`. The same
failure occurs with v2.1.35; the generation contract change in v2.1.36 only
forced that project's first full rebuild in months.

The spilled reduce checks the new generation's edges, references, and
documents against the files and symbols it has just inserted. PostgreSQL had
no statistics for those rows yet, estimated about one row, and chose a plan
that walked every symbol for each probe. One partition of 38,000 edges ran
into the three-minute spill statement timeout. With current statistics the
same statement takes about a tenth of a second.

- The reduce now refreshes the planner statistics of each spill table before
  checking it and of each canonical table after filling it. That project's
  reduce stage drops from a failing three minutes to about one minute, and
  the whole index publishes in under three minutes.
- A statement timeout in the reduce stage is reported as the existing
  `reduce_deadline_exceeded` instead of a reason-less `reduce_failed`, in
  `index --format json` and in MCP admin job status.
- When a failed index cleans up its own staging generation, deleting a very
  large spill (2.6 million rows in that case) can outlast the cleanup
  deadline. Only that deletion is now abandoned: the generation is still
  marked failed and its lease is released, so the next index does not wait
  for the lease to expire. Retention removes the remaining spill rows later.

## Compatibility

The PostgreSQL schema remains **46**, the generation contract remains
**V19**, and the supported ParadeDB service remains **0.25.11**. No database
upgrade is needed from v2.1.36. Run
`cartograph upgrade --apply --project-path <PATH>` to install the release and
reconcile each project.

New stable codes: `schema_busy` (retryable). `cartograph db start` exits with
status 75 when the schema stays busy, and 1 for other failures as before.
Automation that treats every nonzero `db start` status as fatal can retry on
75.

Cartograph remains a native Rust, PostgreSQL-only executable. Release archives
contain no PostgreSQL, ParadeDB, pgvector, database, or container image. There
is no SQLite runtime, importer, optional feature, or fallback.
